**Verdict: `VERL_BUG`** (CI config in the verl repo; regression introduced by PR #7444).

Failure step: `Running nightlyCI_grpo-qwen3-8b-fsdp2-vllm_ascend` — the training
launch itself, before any worker starts. First and only error:

```
File "/__w/verl/verl/verl/single_controller/ray/base.py", line 240, in _check_resource_available
    raise ValueError(
ValueError: Total available GPUs 8.0 is less than total desired GPUs 16
```
(`r32293302531_nightlyCI_gspo-qwen3-8b-fsdp2-vllm_ascend.log` lines 1993–2001)

Chain of evidence:

1. `npu-smi info` at job start lists exactly **8 × 910B3, all Health OK, no
   processes** (log lines 41–89). Ray is right: 8.0 GPUs available.
2. The hydra overrides include `trainer.nnodes=1, trainer.n_gpus_per_node=16`
   (log line 1945) — this comes from
   `tests/special_npu/nightly_ci_ascend/run_gspo_qwen3_8b_fsdp2_npu.sh` line 25
   (`NGPUS_PER_NODE=${NGPUS_PER_NODE:-16}`); the workflow step runs the script
   without an env override.
3. The workflow (`.github/workflows/nightly_ascend.yml:612`) schedules this job
   on `runs-on: linux-aarch64-a2b3-8` — an 8-NPU runner class, matching npu-smi.
4. History: the job was added in #6956 (2026-07-07) on
   `runs-on: linux-aarch64-a3-16` (16 NPUs, a3 image). Commit `b5a35481`
   (PR #7444, "Move lightweight tests to A2 instances", merged 2026-08-17
   06:08 UTC) changed exactly this job's `runs-on` to `linux-aarch64-a2b3-8`
   and its image to the 910B one — but did not touch the script, whose
   `NGPUS_PER_NODE` default stayed 16. The 16-GPU jobs (e.g.
   `run_gspo_qwen3_30b_megatron_npu.sh`) stayed on `a3-16` and are unaffected.
5. Sibling proof: `nightlyCI_ppo-qwen3-8b-fsdp-vllm_ascend` runs the same
   Qwen3-8B model on the same `a2b3-8` label + 910B image with
   `trainer.n_gpus_per_node=8` hardcoded, and reaches training (its 08-19
   failure was a baseline-metric check, i.e. training completed).

Conclusion: deterministic misconfiguration after the runner migration — the
job will fail at startup **every night** until the script is scaled to 8 NPUs
(or the job moved back to a 16-NPU runner, which contradicts #7444's intent).

Dedup: signature
`valueerror-total-available-gpus-less-than-desired-gpus@create_resource_pool`
not in `state/seen-failures.json`; no matching open issue/PR on
verl-project/verl (searched "Total available GPUs is less than total desired
GPUs" and "gspo ascend").

**Fix** (branch `ci-fix/gspo-qwen3-8b-8npu` on fork `lxb007981/verl`, commit
`84e85d6b`): one line, `NGPUS_PER_NODE=${NGPUS_PER_NODE:-16}` → `:-8`.
Divisibility of the untouched defaults checked for 8 GPUs: SP_SIZE=2,
ROLLOUT_TP=2, FSDP_SIZE=-1, train_batch_size 32 (×n=4 → 16 samples/GPU),
ppo_mini_batch_size 16. `bash -n` clean. Not executed on hardware (no NPU).

Follow-up flag for maintainers (in PR body): the job's `check_npu.py` baseline
(`baseline_gspo_qwen3_8b_fsdp2_npu.txt`, stored on the runner, not in the
repo) was recorded on the 16-NPU a3 runner — the first green 8-NPU run may
need a one-time baseline refresh.
