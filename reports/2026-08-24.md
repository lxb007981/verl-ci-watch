(`r32653793181_nightlyCI_grpo_qwen3_vl_8b_Instruct_fsdp2_vllm_ascend.log`):

```

EE9999[PID: 22811] rtDeviceSynchronizeWithTimeout execution failed, reason=hbm Multi-bit ECC error
(Worker_TP0 pid=22809) RuntimeError: synchronize:.../NPUStream.cpp:414 NPU function error:
                       c10_npu::acl::AclrtSynchronizeStreamWithTimeout(stream()), error code is 507011
ERROR ... [async_llm.py:704] vllm.v1.engine.exceptions.EngineDeadError: EngineCore encountered an issue.
```

The `EngineDeadError` then propagated through verl's normal path
(`trainer_base.step` → `checkpoint_manager.sleep_replicas` →
`vllm_async_server.sleep` → `ensure_alive()`) and terminated the job; the
`check_npu.py` step never ran, so this job's usual stale-baseline signature was
**not evaluated tonight**.

- **Root cause**: uncorrectable multi-bit ECC error in HBM on device 1
  (`Worker_TP1`, Device:1) of host `192.168.9.113` — a hardware memory fault.
  Device 0's `507011` sync-timeout is the same event seen from the peer TP rank.
  Nothing in the traceback is verl code misbehaving; verl surfaced the dead
  engine faithfully.
- **Verdict rationale**: INFRA — NPU hardware error, nothing to fix in verl.
  `gh search issues --repo verl-project/verl "HBM MULTI BIT ECC"` → 0 hits, so
  no upstream tracking either.
- **Action for humans**: the device/NPU on 192.168.9.113 that raised the
  multi-bit ECC error should be checked/replaced; expect this job to return to
  its usual stale-baseline-only failure once the host is healthy.
