**Root cause — the baseline was recorded on a 16-NPU pool.** This is the first night
the job is compared against any baseline, so there is no prior A/B history; the
arithmetic settles it. `perf/throughput = total_num_tokens / (time * n_gpus)`
(`verl/trainer/ppo/metric_utils.py:687`, with `n_gpus =
resource_pool_manager.get_n_gpus()` at `verl/trainer/ppo/ray_trainer.py:1785`), i.e.
it is **per-GPU-normalized**. Today's log records `perf/total_num_tokens` 143643–177174
at `perf/time_per_step` 79.3–86.8 s with `n_gpus = 8`. The baseline's implied workload:

- at `n_gpus = 16`: 127.9929 × 79.947007 × 16 = **163,650 tokens/step** → inside today's observed range.
- at `n_gpus = 8`:  127.9929 × 79.947007 × 8  = 81,825 tokens/step → half what the job actually processes.

Same workload, same step time (79.9 vs 83.0 s), same numerics (rewards and probs_diff
in band) — only the GPU-count divisor differs, which is exactly what [#7444]
(2026-08-17, runner move) + [#7456] (`6cbca9ce`, 2026-08-20, `NGPUS_PER_NODE:-16` →
`:-8`) changed. The memory gap points the same way: at 8 GPUs the job carries 4
samples/GPU instead of 2, so peak allocation rises 41.9 → 47.8 GB.

**Verdict: BASELINE_REGRESSION.** Not a verl bug. `baseline/a2/nightly_log/
run_gspo_qwen3_8b_fsdp2_npu/baseline_gspo_qwen3_8b_fsdp2_npu.txt` must be regenerated
from an 8-NPU run of current `main` on the a2b3-8 runner. Note for whoever regenerates
it: because the metric is per-GPU, **each baseline is only valid for one GPU count** —
worth stating in the recipe repo's README so a future runner move doesn't reproduce
this failure mode.
