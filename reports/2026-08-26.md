**Root cause: verl PR #7508 made a long-dead config flag take effect.**

#7508 (commit `82e35343`, merged 2026-08-25 03:58 UTC) fixed
`build_cli_args_from_config` to emit `--no-<flag>` for `Optional[bool]` vLLM
engine args set to `False`. Before it, every `enable_chunked_prefill=False`
was silently **dropped**, so the engine actually ran with chunked prefill
**enabled** (vLLM's default). Both quick_start scripts have carried that dead
flag since they were created in #6900.

The args verl actually emitted this night make the contradiction explicit
(`r32881976946_quick_start_qwen3_0_6b_megatron_vllm_ascend.log`, 18:12:29):

```
'--max_model_len',       '40960',
'--no-enable_chunked_prefill',
'--max_num_batched_tokens', '8192',
WARNING ... [arg_utils.py:2388] This model does not officially support disabling
chunked prefill. Disabling this manually may cause the engine to crash or produce
incorrect outputs.
```

`max_model_len=40960` is verl's own auto-derivation from Qwen3-0.6B's
`max_position_embeddings` (`vllm_async_server.py:995-996`, config left at
`null`), while `max_num_batched_tokens` stays at the 8192 default
(`verl/workers/config/rollout.py:196`). With chunked prefill now genuinely
off, vLLM must prefill a whole sequence in one scheduler step and rejects the
budget.

**Verdict: `VERL_BUG`** — verl-side scripts carry a config that only ever
worked because a verl serializer bug was ignoring it.

**Fix** (branch `ci-fix/quickstart-vllm-chunked-prefill`, head `eeb1813a`,
5 files +12/−4): drop `enable_chunked_prefill=False` from the four Ascend NPU
scripts that set it without a matching token budget, restoring exactly the
configuration those jobs were green with; plus a fail-fast branch in
`vLLMHttpServer._validate_configs` that raises an actionable verl-side
`ValueError` instead of that pydantic traceback.
