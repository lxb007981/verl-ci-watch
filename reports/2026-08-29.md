Peak memory **halved** while speed and quality are byte-in-band — that is a
behavior change, not runner variance, and it is not baseline staleness: B was
regenerated from an 8-NPU run on Aug 27 (recipe commit [284341ca]) and the job
was green on it Aug 27 and Aug 28 nights. Root cause chain:

- **Bracketed by commit.** Last night's green runs were on `662507f9`;
  tonight's are on `24f25b03`. The recipe repo is unchanged since Aug 27
  (`17cabaa4`), the nightly run scripts are untouched in the window, and of
  the seven commits in `662507f9..24f25b03` exactly one touches FSDP
  sync/memory: [`a0feb78f`] (#7458).
- **#7458 contradicts itself.** It adds
  `use_no_sync_for_gradient_accumulation: bool = True` to `FSDPEngineConfig`
  ("keeps its default `true` to preserve the current runtime behavior" of
  [#7095]) but ships `false` in `verl/trainer/config/engine/fsdp.yaml` and in
  all three flattened slots of `verl/trainer/config/_generated_ppo_trainer.yaml`
  (actor, ref, critic). `docs/perf/perf_tuning.rst` and the PR's own usage
  example still document defer-as-default.
- **The runtime proves the YAML wins.** The composed Hydra config dumped at
  startup shows `'use_no_sync_for_gradient_accumulation': False` three times
  (actor/ref/critic, 21:59:39). With the flag off, FSDP2 syncs and reshards
  gradients after *every* micro-batch instead of retaining unsharded grads
  until the final backward — removing precisely the ~27 GB of unsharded
  gradient buffers an 8B model accumulates on 8 ranks. Per-step
  `actor/perf/max_memory_allocated_gb` is a flat 20.67–20.82 GB for all 15
  steps.
- **The FSDP1 sibling corroborates.** [ppo-8b](https://github.com/verl-project/verl/actions/runs/33210244232/job/98981439535)
  composed the same `False`, yet its peak memory is unchanged to six decimals
  (22.2156 vs 22.2318) — FSDP1 accumulates into the flat sharded grad buffer
  either way — ruling out any environmental explanation for the FSDP2 drop.

Verdict `VERL_BUG`: a config regression on `main` that silently disables
#7095's M→1 sync-round optimization for every Hydra-launched FSDP job and
invalidates memory baselines. Fix pushed as
[`ci-fix/fsdp-no-sync-default-true`](https://github.com/lxb007981/verl/tree/ci-fix/fsdp-no-sync-default-true)
(head `bd7e6a85`, four `false`→`true` YAML flips; audit record + PR body in
`state/pending-prs/`). Honest caveat: validation is log-analysis only — no
NPU was available; the verifying job is this nightly (expect ≈ 47.9 GB again).
If maintainers actually prefer per-micro-batch sync as the new default
(tonight's job was marginally *faster* with it), the alternative is a
deliberate default change + baseline regeneration — spelled out in the PR body.
