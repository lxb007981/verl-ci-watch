### nightlyCI_ppo-qwen3-8b-fsdp-vllm_ascend — [run 33536362659](https://github.com/verl-project/verl/actions/runs/33536362659), [job 99951530156](https://github.com/verl-project/verl/actions/runs/33536362659/job/99951530156)

**Failed step:** final checking script, with `ValueError: 日志中无有效step`
("no valid step in log") — training died at rollout-engine init 5 minutes in,
so there were no step metrics to check (`r33536362659_nightlyCI_ppo-qwen3-8b-fsdp-vllm_ascend.log:2529`).

**Root error** — one of the 8 colocated vLLM replicas (TP=1, host 192.168.9.117)
lost a port race inside vLLM's own distributed init
(`r33536362659_nightlyCI_ppo-qwen3-8b-fsdp-vllm_ascend.log:2173-2246`):

```
(Worker pid=20557) ERROR ... WorkerProc failed to start.
  File "/vllm-ascend/vllm_ascend/worker/worker.py", line 992, in _init_worker_distributed_environment
    init_distributed_environment(
  File "/vllm/vllm/distributed/parallel_state.py", line 1609, in init_distributed_environment
    torch.distributed.init_process_group(
torch.distributed.DistNetworkError: The server socket has failed to listen on any
local network address. port: 42121, useIpv6: false, code: -98, name: EADDRINUSE,
message: address already in use
```

`EngineCore failed to start` → `RuntimeError: Engine core initialization failed`
through `vLLMHttpServer.launch_server` → `LLMServerManager.create` → job dead.

**Analysis.** verl launches all 8 replicas concurrently
(`llm_server.py:448` / `vllm_async_server.py:1359`, both via `asyncio.gather`;
long-standing — #7115 at HEAD did not change startup concurrency). The port is
**vLLM-internal**: the `vllm serve` argv carries no distributed-init flag
(`...log:2123-2159`), and verl's race-safe held sockets
(`get_free_port(..., with_alive_sock=True)`) only cover verl's own
master/dp ports. This is exactly verl issue
[#6677](https://github.com/verl-project/verl/issues/6677) (open): vLLM's
single-node `MultiprocExecutor` picks the init port via probe-bind-release
(`get_open_port()`), so two engines starting on one node can collide.
Maintainers concluded it is **not fixable in verl** — vLLM ignores externally
provided ports on this path — and track the fix upstream at
vllm-project/vllm [#39015](https://github.com/vllm-project/vllm/issues/39015);
the two verl fix PRs ([#7230](https://github.com/verl-project/verl/pull/7230),
[#7504](https://github.com/verl-project/verl/pull/7504)) were closed unmerged.

**Verdict: KNOWN** — first manifestation in this nightly in the kit's history
(~15 prior green runs of the same launch path); no verl-side action. Not the
job's usual metric-check signature — that one did not recur (training never
reached step 1). If it recurs, it is worth re-raising on #6677 with the NPU
nightly as evidence.
