### nightlyCI_grpo_qwen3_vl_8b_Instruct_fsdp2_vllm_ascend — [run 34047750735](https://github.com/verl-project/verl/actions/runs/34047750735), [job 101525749042](https://github.com/verl-project/verl/actions/runs/34047750735/job/101525749042)

New signature for this job: **EADDRINUSE in vLLM single-node distributed
init** — died 8 min in, at engine startup, before any training step (the
script step `bash tests/special_npu/run_qwen3_vl_8b_Instruct_fsdp2_npu.sh`
never reached step 1; the checking script never ran).

Evidence (r34047750735_nightlyCI_grpo_qwen3_vl_8b_Instruct_fsdp2_vllm_ascend.log):

- One of the 4 colocated vLLM servers (TP=2 each, single node
  192.168.9.113; server pids 21078/21082/21119/21236) failed worker init at
  17:18:00:
  ```
  (vLLMHttpServer pid=21236) (Worker pid=22979) ... vllm_ascend/worker/worker.py:992, in _init_worker_distributed_environment
      init_distributed_environment(
  ...
  torch.distributed.DistNetworkError: The server socket has failed to listen on any local
  address. port: 37085, useIpv6: false, code: -98, name: EADDRINUSE, message: address already in use
  ```
- EngineCore then aborted → `RuntimeError: Engine core initialization
  failed` propagated through `LLMServerManager.create` →
  `trainer_base.init` (`trainer_base.py:353`) → job exit 1 at 17:18:33.
- Exactly one EADDRINUSE in the whole log; the other 3 servers were
  progressing normally (Gloo ranks connected). The serve argv carries no
  dist-init port flag — the port is chosen inside vLLM.

**Verdict: KNOWN** — verl issue
[#6677](https://github.com/verl-project/verl/issues/6677) (OPEN, "Multiple
vLLM instances on the same node may choose the same distributed init port
and fail with EADDRINUSE"): vLLM's single-node `MultiprocExecutor` picks the
`init_process_group` port via probe-bind-release, so concurrently launching
engines on one node can collide. Maintainers concluded it is **not fixable
in verl** (last comment re-affirms); the fix is tracked at
vllm-project/vllm#39015, and verl-side attempts (#7230, #7504) were closed
unmerged. This is the same signature the ppo-8b sibling job hit on
2026-09-02 (run 33536362659) — tonight is the first occurrence in *this*
job, making it the second nightly job affected.

Ruled out verl code: main is `23af6a7a`, byte-identical to the commit that
ran this job green the previous night ([run 33980113956](https://github.com/verl-project/verl/actions/runs/33980113956),
15/15 steps) — a deterministic code bug is impossible; this is a stochastic
startup race (verl launches the 4 replica servers via `asyncio.gather`,
`llm_server.py:448`).

**Action:** none in verl. A human may want to note on #6677 that a second
nightly job (GRPO Qwen3-VL 8B, TP=2 × 4 replicas) now hits the race —
evidence for prioritizing vllm-project/vllm#39015. (Per policy, no
agent-written issue comment.)
