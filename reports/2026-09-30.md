# verl nightly Ascend CI watch — 2026-09-30

Window covers the 2026-09-29 17:00/18:00/19:00 UTC scheduled runs of `nightly_ascend.yml`,
all at main `3084c261`. All three runs failed; 6 jobs failed, 6 analyzed. **Two distinct
root causes, neither with a safe verl-side auto-fix — no fix branches pushed today.**
Log analysis only; no NPU hardware was available for any reproduction or validation.

- **Cause A (5 of 6 jobs)** — the runner-pool migration in `133454ed` (merged 2026-09-29
  13:29 UTC, "[ci] fix: change runner label for nightly_ascend.yml (#8063)", first commit
  of the new workflow file these runs executed) moved these jobs from `linux-aarch64-a3-800i-*`
  to `linux-aarch64-a3-*`. The new pool's hosts do not provide the modelscope model cache
  (`/root/.cache/modelscope/hub/models/Qwen/<model>`), which is host-mounted, not baked into
  the images (`docker/ascend/Dockerfile.ascend_9.1.0_a3_v0.9.1` contains no weight downloads).
  Every recipe passes the absolute cache path as `model.path`; transformers finds no local dir,
  falls back to hub download, and the absolute path fails repo-id validation → instant crash
  at tokenizer/config load.
- **Cause B (1 of 6 jobs, latent in a 2nd)** — `f1db883c` (merged 2026-09-29 08:11 UTC,
  "[BREAKING][megatron] refactor: remove legacy mbridge support (#8051)") deleted the
  `vanilla_mbridge` code path and stripped `vanilla_mbridge=True` from the Ascend scripts.
  The sglang Ascend image still ships only `mbridge 0.15.1` (no `megatron-bridge`), so megatron
  jobs on that image now die on `from megatron.bridge import AutoBridge`.

Negative controls from the same day: [36536151135](https://github.com/verl-project/verl/actions/runs/36536151135)
(PR-triggered, 2026-09-29 07:21–12:07 UTC, pre-migration labels) ran
`nightlyCI_grpo_qwen3_5_2b_fsdp_turbo_vllm_ascend` to **success** on the old pool — the exact
job that failed at 19:13 on the new pool. In [36609993822](https://github.com/verl-project/verl/actions/runs/36609993822),
`quick_start_qwen3_0_6b_megatron_vllm_ascend` and both fsdp2 quick_starts **passed** (old
pool / vllm image) while `quick_start_qwen3_0_6b_megatron_sglang_ascend` failed on the
mbridge import — isolating each cause cleanly.

Verdict **DEPENDENCY** (Ascend sglang image lags what verl main now requires), triggered by
verl's intentional BREAKING refactor. Why no auto-pushed verl-side workaround branch:

- PyPI `megatron-bridge` 0.5.0 declares `requires-python >=3.12,<3.13` and a heavy dep tree
  (`transformers<5.9.0`, `megatron-core[dev,mlm]`, flashinfer…); the sglang image runs
  **Python 3.11.14** with transformers 5.12.1 and megatron-core 0.16.2 — a plain/`--no-deps`
  pip step is blocked or version-conflicted, and the working vllm image pairs bridge 0.5.0
  with mcore **0.18.0**, not 0.16.2. A deps-free git clone (mirroring the image bake) still
  needs `megatron-energon` + `nvidia-modelopt` (bridge hard-imports them per verl's own
  pyproject notes) with no aarch64/Ascend-mirror guarantee. Every variant has ≥2 untestable
  compat gates (no NPU here), so a guessed shim risks wasting maintainer time and masking
  the real fix.
- Restoring the vanilla path would revert a deliberate BREAKING refactor landed hours
  earlier with follow-ups already stacked ([2/N] `036baac9`).

Recommended fix (for the human/Ascend-CI team): rebuild `latest-sglang-a3-ubuntu` with the
same Megatron-Bridge stack the vllm image already bakes (megatron-bridge + megatron-energon +
nvidia-modelopt), or pin bridge provisioning in the job; nothing to fix in the runner script.
**Also latent:** `nightlyCI_grpo-qwen3-30b-megatron-sglang_ascend` runs on the same sglang
image and lost `vanilla_mbridge=True` in the same commit — it will fail identically the
moment the model cache is restored (see next-but-one entry).
