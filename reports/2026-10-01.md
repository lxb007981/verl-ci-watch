reward 0.4747 (family 0.47-0.49), probs_diff_mean 0.0053-0.0056 dead-on vs
baseline 0.005523, aborted_ratio 0.0. The check step never ran (no `if:
always()`; the training step failed first).

The real error is a single line at 17:53:22, mid-run, ~4.5 min before the end —
`r36749889623_nightlyCI_grpo_qwen3_vl_8b_Instruct_fsdp2_vllm_ascend.log:2787`:

```
tee: /root/.cache/nightly_log/run_qwen3_vl_8b_Instruct_fsdp2_npu/run_qwen3_vl_8b_Instruct_fsdp2_npu.log: No such file or directory
```

Mechanism, reconstructed:

1. `run_qwen3_vl_8b_Instruct_fsdp2_npu.sh` runs `python3 … | tee $LOG` under
   `set -xeuo pipefail` (unlike most nightly scripts, which lack `pipefail`).
2. At 17:53:22 the log path was **deleted from under the running job** — the
   step:10-12 metric lines were tee'd fine seconds earlier, and an open fd
   survives a plain unlink, so the *directory* `/root/.cache/nightly_log/
   run_qwen3_vl_8b_Instruct_fsdp2_npu` was removed/replaced externally (who
   removed it is not recoverable from CI logs — it is shared runner-side state
   on the node). GNU tee reported the write failure, kept relaying to stdout
   (all later training output is present in the Actions log), and exited **1**
   at EOF.
3. Python itself finished cleanly (exit 0). The trailing
   `Exception ignored in atexit callback … RuntimeError: DataLoader worker …
   killed by signal: Killed` (log:2808-2823) is the long-documented benign
   teardown print — byte-identical on the green 2026-09-28 night (fetched job
   [109044486112](https://github.com/verl-project/verl/actions/runs/36456623459/job/109044486112)),
   and a local CPython 3.12 test confirms an exception in an atexit callback
   leaves the exit code 0 — it did not fail the step.
4. `pipefail` turned tee's exit 1 into the step's exit 1 (log:2830-2832,
   `##[error] … exit code: 1` at 17:57:29) → check step skipped → job red.

This is the **4th observed loss of this job's tee'd log** on tvqbd — the same
underlying phenomenon as the "empty tee log at check time" nights of 2026-09-03/
09-10/09-11 (the reason the workflow's check step carries a wait-loop + `ls -l/
wc -c/tail` diagnostics from #7852). Tonight the deletion hit mid-run and
`pipefail` surfaced it as a training-step failure instead of the usual check-step
`日志中无有效step`.

verl code is exonerated: the window since the last two green nights
(`00094bd9` 09-28, `3084c261` 09-29) contains only `fbb4b3a8` (fp8-only weight
sync, no-op for this bf16 job), `464de383` (veomni/GPU-CI), `133454ed` (labels;
this job's label and node pool unchanged).

Counterfactual (check never ran; computed from step:10-15 lines vs current
baseline 41.47/87.84/164.24/0.384750/0.005523): memory A=39.467 vs B=41.47 =
**-2.00 GB, beyond the ±1 threshold — the memory check would have failed
anyway** (the documented post-#7428 low-token-draw flap, `B` calibrated on a
high-draw night); the other four metrics sit in band (throughput ~167.6 vs
164.24, step ~84 vs 87.84, rewards ~0.40 vs 0.385, probs dead-on). So the job
would very likely have been red tonight regardless — through the known recipe
threshold issue, not a verl defect.

Verdict **INFRA**. Action (runner-admin, not verl): stop whatever cleans
`/root/.cache/nightly_log/*` on tvqbd while jobs are in flight; the path needs
per-job isolation or no mid-flight GC. No verl-side change: making the pipeline
tolerate tee failure would mask real log loss.
