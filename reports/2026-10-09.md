### nightlyCI_grpo_qwen3_5_2b_fsdp_turbo_vllm_ascend — [run 37721374062](https://github.com/verl-project/verl/actions/runs/37721374062), [job 113132784875](https://github.com/verl-project/verl/actions/runs/37721374062/job/113132784875)

**Context: this is not a scheduled run.** It is the first CI run of open PR [#8057](https://github.com/verl-project/verl/pull/8057) ("[fsdp] feat: make FSDP2 CPU offload pin_memory configurable", merge commit `3bf62ff8` = PR head `7ee8d94f` into `acad9875`), which adds a `pull_request` trigger for this job and moves it back to the cached `a3-800i-8` pool — so it ran on tvqbd at 03:23 UTC and got further than the scheduled main runs have in 10 days (model + tokenizer loaded, engines initialized, training started).

**Failure** — first optimizer step of training, ~14 min in (`r37721374062_nightlyCI_grpo_qwen3_5_2b_fsdp_turbo_vllm_ascend.log`):

```
engine_workers.py:369 train_batch -> engine/base.py:128 train_batch -> optimizer_step
  -> verl/workers/engine/fsdp/fsdp_turbo_impl.py:124
     grad_norm_value = clip_grad_norm(model=self.module, max_norm=...)
  -> /FSDPTurbo/fsdp_turbo/training/clip_grads.py:259 clip_grad_norm
  -> /FSDPTurbo/fsdp_turbo/training/clip_grads.py:112 compute_grad_norm
       dev = torch.accelerator.current_device()
AttributeError: module 'torch.accelerator' has no attribute 'current_device'.
Did you mean: 'current_device_idx'?
```

- torch in the image is 2.10.0 / torch_npu 2.10.0.post4 (log:387-388), unchanged from prior nights.
- The workflow's "Clone FSDPTurbo" step in this run was the **unpinned** `git clone https://gitcode.com/Ascend/FSDPTurbo.git /FSDPTurbo` (log:601-614) — i.e. FSDPTurbo@HEAD.

**Root cause (DEPENDENCY):** FSDPTurbo upstream commit `3fd503c` introduced `torch.accelerator.current_device()` in `compute_grad_norm`, an API that does not exist in torch 2.10 (which has `current_device_idx`). verl's call site (`fsdp_turbo_impl.py:122-124`, unchanged since #7633) is a thin passthrough into that package. The scheduled main job would hit the identical crash at its first optimizer step once it gets past the a3-8 cache miss, because main's workflow also clones FSDPTurbo unpinned.

**Why KNOWN and no branch from this kit:** PR #8057's author hit exactly this failure and pushed a follow-up (PR head `cbe21f44`, ~06:39 UTC) that pins the clone to `0a4b3bc3` — the comment in the workflow says verbatim *"Pin to the commit right before 3fd503c, which calls torch.accelerator.current_device() and breaks on torch 2.10"*. The updated PR run then passed this job green: [run 37738830461](https://github.com/verl-project/verl/actions/runs/37738830461), [job 113188274079](https://github.com/verl-project/verl/actions/runs/37738830461/job/113188274079) (24m58s, full training + metric check). A kit branch duplicating that pin would be redundant; `gh search` finds no separate upstream issue. **Watch item:** until #8057 merges, main's scheduled fsdp_turbo runs carry a second latent breakage behind the cache miss.

Side observation from the same PR (relevant to the standing host-pinned-OOM family): #8057 also sets `fsdp_plan.pin_memory=False` in the fsdp_turbo recipe and adds an `offload_pin_memory` engine knob — its green run trained with pageable host offload on tvqbd, uncontended. That addresses verl-side FSDP offload pins; it does **not** cover the vLLM-Ascend camem-sleep pinned allocation that killed job 2 below.
