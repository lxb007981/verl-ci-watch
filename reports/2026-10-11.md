First run of this job after [#8162](https://github.com/verl-project/verl/pull/8162)
(`22d59423`, merged 2026-10-10 04:57 UTC) reshaped
`tests/special_npu/run_qwen3_vl_8b_Instruct_fsdp2_npu.sh`:
`n_devices_per_node` default 8 → **16**, `TRAIN_BATCH_SIZE` 16 → 32,
`PPO_MINI_BATCH_SIZE` 8 → 16, and moved the e2e twin job
(`e2e_ascend.yml` `llm_rl_job`) to `linux-aarch64-a3-800i-16`. The **nightly**
job was left on `runs-on: linux-aarch64-a3-800i-8`. Died 4.5 min in at
resource-pool creation, before any model load — the runner
(`linux-aarch64-a3-800i-8-cn12-001-tvqbd-runner-r8t4s`) exposes 8 NPUs while
the recipe now requests 16 (`trainer.n_gpus_per_node=16` in the hydra overrides,
`r38070730987_nightlyCI_grpo_qwen3_vl_8b_Instruct_fsdp2_vllm_ascend.log:2028`):

```
verl/trainer/ppo/v1/trainer_base.py:231 _setup
  -> verl/single_controller/ray/base.py:247 _check_resource_available
ValueError: Total available NPU 8.0 is less than total desired NPU 16
```
(`r38070730987_nightlyCI_grpo_qwen3_vl_8b_Instruct_fsdp2_vllm_ascend.log:2128-2132`)

Root cause: verl CI config inconsistency introduced by #8162 (script defaults
moved to 16 devices; nightly workflow's runner label not updated) — in
isolation this would be a one-line `VERL_BUG` fix
(`runs-on: linux-aarch64-a3-800i-16`). However, open PR
[#8188](https://github.com/verl-project/verl/pull/8188) ("[ci] chore: Move
selected Ascend FSDP2 jobs to 16-NPU runners", `fix_host_oom`, updated
2026-10-10 10:17 UTC) already moves exactly this job to `a3-800i-16` with
`--shm-size 160g`, explicit `NDEVICES_PER_NODE=16 TRAIN_BATCH_SIZE=32
PPO_MINI_BATCH_SIZE=16`, and a temporary `pull_request` trigger to validate
the three moved jobs before merging (its CI run
[38044417060](https://github.com/verl-project/verl/actions/runs/38044417060)
is `action_required`, awaiting runner approval). Verdict **KNOWN** — no kit
branch, it would duplicate #8188.

Two follow-ups for whoever reviews #8188 (also flagged in the signature note):
the 8-NPU-era recipe baseline is stale once the shape doubles (expect a
BASELINE_REGRESSION night until verl-ascend-recipe regenerates it), and if the
`a3-800i-16` pool lacks the Qwen3-VL-8B modelscope cache the job will trade
this error for a cache-miss. `gh search` for the error text finds no separate
issue.
