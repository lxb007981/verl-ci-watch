`TRAIN_BATCH_SIZE=32`/`PPO_MINI_BATCH_SIZE=16`; runner `nvbsd ph8f7`, 19:13 batch). Training
perfectly healthy: 15/15, per-step memory ~13.0 GB, benign teardown. The check script then failed
on a **single metric — perf/throughput** (r38453028346 log:2818-2830):

```
【内存，超出基线>1GB】actor/perf/max_memory_allocated_gb  | A=13.192257 B=20.825053 | 差值=-7.632796
【性能，下降幅度<=5%】perf/throughput                    | A=150.109456 B=247.402200 | 变化=-39.33%

【精度，变化率<=5%】training/rollout_probs_diff_mean     | A=0.004562 B=0.004535    | 变化=0.60%
AssertionError: 指标校验失败，不达标项：
  - perf/throughput 变化率 -39.33%，下降超过阈值5%
```

Root cause — **stale 8-NPU baseline meeting the intended 16-NPU topology**, not a perf
regression: verl computes `perf/throughput = total_num_tokens / (time * n_gpus)`
(`verl/trainer/ppo/metric_utils.py:687`), i.e. **per GPU**. Doubling `n_gpus` at constant global
batch mechanically halves it: predicted from B = 247.4 × (8/16) × (83.03/69.57) = **147.6** vs
observed A = 150.1 — the entire -39.33% is topology × the ~19% faster steps. Everything else
confirms health and most metrics *improved*: memory -7.63 GB (halved FSDP2 shard, on the "good"
side of a >1 GB over-baseline check), step -16.2% (faster), rewards and probs dead-on in band.
The check still fetches the a2-pool 8-NPU-era recipe baseline
(`.../a2/nightly_log/run_gspo_qwen3_8b_fsdp2_npu/baseline_gspo_qwen3_8b_fsdp2_npu.txt`, both
curls ~1 s). This is exactly the failure mode the qwen3_vl WATCH note predicted for 16-way moves;
`gh search` shows no upstream issue/PR for it (only merged #8188 itself).

Action (recipe-side): regenerate `baseline_gspo_qwen3_8b_fsdp2_npu.txt` from a green 16-NPU run,
or make the check topology-aware. Expect red nightly until then. The same exposure applies to
qwen3_vl's 16-way check whenever it first runs (masked tonight, see below). No verl code change.
