#### Root cause: `95ede340` (#8780) removed the staging that the NPU refit path relied on

1. vllm-ascend keeps unquantized expert weights transposed. `AscendUnquantizedFusedMoEMethod.process_weights_after_loading`
   does `w13_weight.transpose(1, 2)` and `w2_weight.transpose(1, 2)` and replaces the parameters, so the live
   weights are `[E, H, 2I]` / `[E, I, H]` (vllm-ascend `vllm_ascend/ops/fused_moe/routed_experts.py:107-111` at the
   image's commit `a2ed69c2b3`).
2. A refit sends checkpoint-layout tensors. vLLM 0.30.0's `_load_w13` (`routed_experts.py:459-508`) slices the
   `[768, 2048]` expert weight to this rank's `[96, 2048]` (768 / TP 8), then narrows the live slot as if it were
   `[2I, H]`: dim 0 to `2048 // 2 = 1024`, and once more to the loaded slice's 96. That gives `[96, 192]` — the two
   shapes in the error.
3. Before #8780, `stage_unquantized_moe_params` gave the loads a checkpoint-layout view over the live storage on
   every device, and `fold_unquantized_moe_params` put the kernel layout back after the last bucket.
4. #8780 deleted both and brackets the bucket stream with vLLM's `start_reload` / `finish_reload` instead — on
   non-NPU devices only. NPU was left with the bare `process_weights_after_loading` path ("NPU keeps its
   `process_weights_after_loading` path", per the PR). That cannot work here: vLLM 0.30.0 has no `start_reload`
   (`vllm/model_executor/model_loader/reload/__init__.py` exports only the older `initialize_layerwise_reload` /
   `finalize_layerwise_processing`), which is why the PR kept NPU on a separate branch in the first place.
5. The PR's tests ran on GB200 with vLLM 0.34.0 only.
